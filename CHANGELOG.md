# Changelog

This file records all notable changes to this project. The format follows Keep a Changelog 1.1.0. The project uses semantic versioning. Each entry starts with the part that it changes: the package, the core module `bridge`, a bridge such as `vscode`, or the repository. Each release names the version of zig-sdk that it pins.

## [Unreleased]

### Fixed

- `bridge`: the test of two messages in one chunk accepts the list changes of a listen stream after the result of `initialize`. A `notifications/initialized` in the same read can be handled after the result, when the reader lags the upstream server. The correction to the notes of 0.1.2: that release does not give an exact frame count for this test. The cause was observed on macOS ReleaseSafe: the frames were the result, the three list changes and the ping result.

## [0.1.2] - 2026-10-09

### Fixed

- `bridge`: a `notifications/initialized` that reached the front end before the `initialize` result could start the listen stream. The state becomes `ready` a little before the result goes out, and the listener started in that window. The listener now starts only after the result, as the doc of the front end says. Such a notification gets no list changes, and the test of the two messages in one chunk has an exact frame count again.

## [0.1.1] - 2026-10-09

### Changed

- Package: the pin of zig-sdk moves to the commit `52fc1b83c5f70f9e6a1fc2f1e2e71250656672cc` of the tag `v0.5.1` of zig-sdk. That release has the fixes of `mcp.util.wake.wakeIp` and of the stop of the servers after a cancel. Before, the pin was an untagged commit of zig-sdk pull request #36.
- Package: from zig-sdk 0.5.0, the Secret Service backend of the keychain has time limits. Each answer of the Secret Service has a limit of 25 seconds, and a prompt to the user has a limit of 5 minutes. At a limit, the keychain store of the bridge gets `error.KeychainUnavailable` or `error.KeychainLocked`.

### Fixed

- `bridge`: on macOS, the stop of the loopback receiver after a cancel does not stop a Debug build with the panic `programmer bug caused syscall error: ISCONN`. The pinned zig-sdk connects the wake connection of `cancelAcceptLoop` with a socket that does not block. Before, a late cancel signal of std could interrupt the connect, and the second connect of std got `EISCONN`.
- `bridge`: the loopback receiver of the sign-in ignores a cancel while it waits in `accept`. Only the wake connection of `Receiver.stop` ends that wait. On Windows, the cancel of the stop could arrive just after the accept took the wake connection. Std then closed that connection, and a Debug build wrote a stack trace of `error.Unexpected` with the status `INVALID_PARAMETER` to stderr. These lines have no tag of the bridge.

## [0.1.0] - 2026-10-08

This section has the work of milestones M0 to M5. M0 is the scaffold: the package, the build, the tools and the documents. M1 is the runtime of the `vscode` bridge over stdio. M2 and M3 send the input requests and the notifications of the upstream server to the client. M4 adds an upstream server at an HTTPS URL, with the OAuth sign-in and the storage of the tokens. M5 puts the bridge into the executable of a zig-sdk server, so that one executable serves the two revisions.

The bridge starts the upstream command, or it connects to the upstream server at a URL over Streamable HTTP. When the server at the URL asks for it, the bridge signs in at its authorization server. The bridge answers `initialize`, and forwards the requests for tools, prompts, resources and completion. It also forwards the progress notifications and the cancellations.

When the upstream server asks for input, the bridge sends each input request to the client and sends the answers to the upstream server. A listen stream gives the list changes and the resource updates of the upstream server to the client. The log messages of the requests also go to the client. The pin of zig-sdk is the commit `8334b15` of zig-sdk pull request #31, before the tag `v0.4.0`.

Milestone M6 protects the sign-in on a POSIX host that other users share. On such a host, other users can read the arguments of the browser opener. Thus the browser now gets a one-time start URL in place of the authorization URL.

### Added

- Package: the Zig package `bridge_sdk` for Zig 0.16.0. Its only dependency is zig-sdk. `build.zig.zon` pins the commit `8334b1501644c9f8e1f65f7e24b1ef86b335093f` of the tag `v0.4.0` of zig-sdk, with the package hash. M0 to M2 used zig-sdk v0.3.0 (`c1f55f00deefb3f09ac97126d6405b1820b927dd`). The `.paths` list has `build.zig`, `build.zig.zon`, `src`, `bridges`, `LICENSE`, `NOTICE` and `README.md`.
- Package: the package exports the `mcp` module of the pinned zig-sdk, so that an embedder can use the same `mcp` types as the bridges.
- `bridge`: the core module in `src/bridge.zig`. `bridge.Profile` holds the settings of one product, for example its name, the `_meta` keys for the upstream server and the quirk flags. `bridge.version` is the version of the package.
- `bridge`: the quirk `drop_non_object_output_schema` of `bridge.Profile`. It removes each tool `outputSchema` whose root does not have `type: "object"`.
- `bridge`: `bridge.legacy`, the part of revision 2025-11-25 that a bridge receives from its client. It parses the params of `initialize`, `logging/setLevel`, `resources/subscribe`, `resources/unsubscribe` and `notifications/cancelled`, and it gives the kind of each method.
- `bridge`: `bridge.translate`, the translation without I/O. It has the capability masks for the two sides. It makes the `initialize` result from the `server/discover` result. A forwarded request loses `task`, and its `_meta` keeps only the keys that `translate.passMeta` passes.
- `bridge`: the result rules of `bridge.translate`. A result loses `resultType`, `ttlMs`, `cacheScope` and the server information in `_meta`. A list result loses a `nextCursor` that is not a string.
- `bridge`: the schema rule R6 of `bridge.translate`. Each array schema of a tool `inputSchema` gets `items: {}` when its `items` is missing or false in JavaScript. The bridge writes one log line for each change.
- `bridge`: a `tools/call` result always has a `content` array. When it has `structuredContent` and no text block, it gets a text block with the serialized `structuredContent`.
- `bridge`: the error table of `bridge.translate`. Each error of the bridge has a fixed message, a JSON-RPC code and `data.cause`. An upstream error goes to the client without a change, except -32042 and a -32602 that refuses the `requestState` of a round. The cause `invalid_meta` (-32602) is for a `_meta` key that zig-sdk refuses.
- `bridge`: `bridge.Frontend`, the legacy stdio server for one client connection. It has the lifecycle states `awaiting_initialize`, `initializing`, `ready` and `closing`, and only the first `initialize` starts the upstream server.
- `bridge`: `bridge.Frontend` answers `ping` and `logging/setLevel` itself, and it answers `server/discover` with -32601. It sends the progress of the upstream server to the progress token of the client. It sends a cancellation of the client to the upstream server.
- `bridge`: the `initialize` result of `bridge.Frontend` declares `listChanged`, `resources.subscribe` and `logging` exactly when the upstream server declares them. `translate.ReplyMask` can remove them, and `translate.declared` gives them to the front end.
- `bridge`: the reader of `bridge.Frontend` never waits. At the limit of requests in flight, it answers a new request with -32603 at once. A canceled request gets no response.
- `bridge`: the line reader of `bridge.Frontend` keeps the start and the end of a line that is too long. The error for a line that is not valid has the id of the request, also when the id is the last member.
- `bridge`: when the upstream server stops, `bridge.Frontend` answers each request in flight with -32603 and stops. At the end of the input, it cancels the requests in flight and stops in `shutdown_grace`. `Frontend.Hooks` lets an executable act on these two events.
- `bridge`: `bridge.Upstream`, the `mcp.Client` of zig-sdk and its transport: stdio, Streamable HTTP, memory or a transport of the caller. On stdio, `max_restarts` is 0 and the line limit is 64 MiB. `gone`, `reap` and `pid` tell the state of the child process. `reap` gives the exit status that zig-sdk records when it reaps the child process. zig-sdk sends no signal to a process after its reap.
- `bridge`: the HTTP transport of `bridge.Upstream` (M4). `Config.Http` has the URL, the extra headers, the provider of the sign-in, the trust and the proxy of the environment. Its `max_response_bytes` (64 MiB) applies to each JSON response and to each event of a stream. `loadCaBundle` adds the CA certificates of a PEM file to the CA store of the system. Over HTTP, `gone` is always false: a failed request fails alone, and the bridge continues. `isRemote` is true for HTTP.
- `bridge`: the debug log lines of `bridge.Upstream`. Each upstream exchange gives one line with the round, the method, the outcome and the time, but no content of a frame.
- `bridge`: `bridge.input`, the input requests of the upstream server (M2). `bridge.Frontend` sends each upstream request with `allow_input_required` and does the rounds itself. It sends all input requests of a round to the client at one time. Each one is an `elicitation/create`, `sampling/createMessage` or `roots/list` request with a string id such as `b-1`. Then it sends the upstream request again with `inputResponses` and `requestState`.
- `bridge`: the capability mask of `bridge.translate` declares sampling, elicitation and roots to the upstream server as the client declares them. It never adds `sampling.tools` or `sampling.context`, and it removes `roots.listChanged`.
- `bridge`: the checks of an input request before the client gets it. The client must declare the kind of the input request. A sampling request with tools needs `sampling.tools`, and its messages must obey the tool result rules. A failed check fails the original request with -32603, and `data.detail` names the key of the input request. The client then gets no request of the round.
- `bridge`: the URL rule. The client gets only an `https` URL, or an `http` URL to a loopback host. The bridge refuses a URL with a backslash and an `http` URL with user information. A web browser can find a different host in such a URL. For each other URL, the upstream server gets `{"action":"decline"}`, and the bridge writes a warning.
- `bridge`: VS Code cannot show a form without a property. For such a form, the client gets a form with the message of the server and the one required choice "Continue". When the user accepts, the upstream server gets `accept` with empty content.
- `bridge`: the checks of the answers of the client. An elicitation result loses `content` unless the action is `accept`, and a URL result always loses `content`. The accepted content of a form must be valid against its `requestedSchema`. A roots result loses each URI that does not start with `file://`. An error of the client gives `{"action":"cancel"}` for an elicitation, and it fails the original request for sampling and roots.
- `bridge`: each URL elicitation gets an `elicitationId`. After the user accepts the URL, the client gets `notifications/elicitation/complete` when an upstream round no longer asks for that URL. The client also gets it when the original request ends with an error or a cancellation. When a later round asks again for an accepted URL, the client does not get the URL again. It gets a form with the one required choice "Continue".
- `bridge`: the upstream server can refuse the `requestState` of a round with -32602. A `tools/call` then gets a result with `isError: true` and a text that tells the user to run the tool again. Another method gets an error with that text and the upstream data.
- `bridge`: the pending table of `bridge.Frontend` for the requests of the bridge to the client. The reader puts each answer into the table at once, and it drops an answer with an unknown, numeric or null id. A line that is not valid and that has the id of a request of the bridge resolves that request. The bridge sends `notifications/cancelled` for each request of the bridge that went out and has no answer. It does this on a cancellation, a timeout, the end of the input or the loss of the upstream server. The reason of the cancellation tells which of these events occurred.
- `bridge`: while a request waits for the answers of the client, the log line about the wait names the client and not the upstream server. An error of the client for a sampling or roots request gives an info line and not a warning. The refusal of the user is an example of such an error.
- `bridge`: the limits of the input requests. `Frontend.Options.max_input_requests_per_round` (default 16) limits the input requests of one round. `Frontend.Timeouts.input` (default 1 h) limits the wait for the answers of one round. `mrtr_max_rounds_client` of zig-sdk (10) limits the rounds of one request. The error causes `invalid_input_request`, `too_many_input_requests`, `input_timeout` and `invalid_client_answer` are new.
- `bridge`: `bridge.notify`, the listen stream of the upstream server (M3). After `notifications/initialized`, `bridge.Frontend` opens one `subscriptions/listen` stream for the list changes and the subscribed URIs that the `initialize` result declares. One owner task holds the streams and the URIs. Each stream has its own task and arena.
- `bridge`: the client gets only `notifications/tools/list_changed`, `notifications/prompts/list_changed`, `notifications/resources/list_changed` and `notifications/resources/updated` of the listen stream, without the subscription id. The client never gets a `notifications/cancelled` of the upstream server, because the ids of the two sides can be equal.
- `bridge`: after the acknowledgment of the first stream and of each stream after a loss, the client gets one list change for each declared list. It also gets one `notifications/resources/updated` for each subscribed URI, because the upstream server does not send the events of a gap again. A second acknowledgment in one stream, after a hidden new attempt of zig-sdk, also gives them. A change of the subscriptions alone gives no list change and no update.
- `bridge`: after a loss, the bridge opens a new listen stream after a wait. The wait starts at `Frontend.Options.listen_backoff` (0.5 s) and doubles up to `Frontend.Options.listen_max_backoff` (30 s). Only a stream that lives for 10 s after its acknowledgment resets the wait. Thus an upstream server that ends each stream at once gets the new streams after longer waits. A cancellation, a JSON-RPC error and the end of the upstream server stop the new attempts.
- `bridge`: `resources/subscribe` and `resources/unsubscribe` change the URIs of the listen stream, one change at a time. The acknowledgment of the new stream writes the response `{}`, and then the bridge cancels the old stream. An event of the old stream does not go to the client after that response. An old stream that acknowledges late does not take the place of a newer stream. When the new stream fails, the old stream and the old URIs stay, and the client gets the error.
- `bridge`: on stdio, the listen stream uses `RequestOptions.inline_notifications` of zig-sdk. Thus a list change that the upstream server writes before the result of a call reaches the client before that result.
- `bridge`: `logging/setLevel` gives the log level of each upstream request (`RequestOptions.log_level`). On stdio, the log messages come through the `on_notification` spawn option of the stdio client. That function gives only `notifications/message` to the client and drops each other notification. On the memory link, each request gives its log messages to `on_log`. `Frontend.forwardLog` sends them to the client as `notifications/message` with `level`, `logger` and `data`.
- `bridge`: the `_meta` keys of the client that the profile allows go to the upstream server (`RequestOptions.meta`). `translate.passMeta` removes each key that `validateKey` refuses and each key of zig-sdk, thus such a key does not make the request fail. It also removes each key with a reserved prefix.
- Repository: the fixture tools `toggle`, `toggled`, `touch` and `log`, the fixture prompt `toggled` and the fixture resource `file:///fixture/notes.txt`. The fixture server declares `logging`. The executable also has the tool `shutdown`. It ends the listen streams as at the end of the input, and then it stops the process with exit code 0.
- Repository: the tests of the notifications. They are the unit tests of `bridge.notify` with a scripted upstream transport, the transcript tests in `bridges/vscode/test/notify_test.zig` and four process tests. One process test calls a tool that changes the tool list 1000 times, and each list change must come before its result. The interop check and the fuzz target of the front end also have notifications.
- `bridge`: `bridge.oauth`, the sign-in at an HTTP upstream server (M4). `validateAuthorizationUrl` checks each authorization URL before the bridge writes it or opens it. The URL must use `https`, have a host and have no user information. It has only visible ASCII characters without ``"<>\^`{|}``, and at most 8 KiB.
- `bridge`: the browser opener of `bridge.oauth`. It calls `ShellExecuteW` on Windows, and `$BROWSER`, `open` or `xdg-open` with the URL as the only argument on the POSIX systems. It never starts a shell. The program of the POSIX opener gets stdin and stdout on the null device and no secret variable of the environment. On Windows, the URL form removes these variables from the environment of the process.
- `bridge`: the loopback receiver of `bridge.oauth`. It listens on `127.0.0.1` before the browser opens, never with `reuse_address`, and with `SO_EXCLUSIVEADDRUSE` on Windows. Only a `GET` of the callback path with the expected `state` ends the wait. Each connection has a limit of 16 KiB and 10 s for its request head. The accept loop uses the wake pattern of zig-sdk. The wait ends at the time limit, at a cancel and at the end of the input.
- `bridge`: `SignIn`, `Gate` and `Authorizer` of `bridge.oauth`. Before `notifications/initialized`, the first sign-in opens the browser. After it, the client gets a URL elicitation, and the bridge never opens the browser itself. A declined sign-in starts a cooldown of 60 s for all scopes. `max_step_up_attempts` is 1. The provider records the cause of each challenge that it did not answer, for the error of the request.
- `bridge`: the registration order of `bridge.oauth`: a pre-registered client, then a client ID metadata document, then dynamic client registration. The storage identity has the name of the bridge, the account and the redirect URI. A pre-registered client and a document that is not the document of the bridge add a suffix.
- `bridge`: `TokenStore` of `bridge.oauth`. `auto` tries the keychain of the host first, then the file store with a key from outside the token directory, then memory. A keychain that stops to answer later switches to the next store for the rest of the process. `IndexedStorage` keeps an index of the stored sign-ins in the same store. `logout` and `logoutAll` read it. Without an entry, `logout` finds the key through the protected resource metadata, when its resource covers the URL.
- `bridge`: `bridge.translate.IconRule` and `filterIcons`. For a remote upstream server, the client gets only the `data:` icons of the server, of its tools, of its prompts and of its resources.
- `bridge`: the error causes of the sign-in in `bridge.translate`, for example `sign_in_timeout`, `registration_unavailable`, `redirect_port_unavailable`, `reauthorization_required` and `sandbox`. Each message names the option to use. A message never has the URL of the upstream server, because its path or its query can hold a key.
- `bridge`: over HTTP, `bridge.notify` opens a new listen stream after the status 408, 429 and 5xx except 501. After 401 or 403 with a sign-in, it waits for the next sign-in of a different request, and never for a timer.
- `bridge`: `server/discover` waits for `--discover-timeout` and the time limit of the sign-in together, when no stored access token is valid for more than one minute. When the time limit of `server/discover` stops a sign-in, the error names the sign-in.
- `bridge`: the HTTP status of a failed request to an upstream server at a URL, for example "HTTP status 404". It is in the `data.detail` of the error and in the line `server/discover failed`. The status comes from `Diagnostics.http_status` of zig-sdk.
- `bridge`: `bridge.Frontend` blocks the cancel of its task during a write to the client. Before, a cancel during the write could leave the task of an HTTP stream in its read. The end of the input then waited for that task.
- `bridge`: `bridge.log`, the log function of the executables. Each stderr line has a fixed tag, the scope and the level. `bridge.log.setLevel` changes the level at run time.
- `bridge`: `bridge.embed`, the bridge in the process of a zig-sdk server (M5). `serveStdioAuto(io, gpa, server, in, out, options)` serves one stdio connection for a client of revision 2025-11-25 or of revision 2026-07-28. The first request selects the path. `initialize` selects the legacy path: a `Frontend` with the profile of `Options.profile`, and the same server as its upstream server through `mcp.transport.memory.ClientLink`. Each other message selects the stdio transport of zig-sdk, also a line that is not valid JSON-RPC.
- `bridge`: the first line of `bridge.embed`. The function reads it with the line framer and the line limit of the server, and it drops a line that is too long. `embed.classify` parses it with the depth limit of the server. Only a request with the method `initialize` selects the legacy path. The path reads the next lines from the same reader, thus it gets each byte after the first line.
- `bridge`: a `server/discover` request before the first other request selects no path in `bridge.embed`. The server answers it (`Discover.answer`, the default). With `Discover.refuse`, the bridge answers -32601. A client of the two revisions, such as the Copilot harness of VS Code, then takes the legacy path. A client that sends its next request without the result of `server/discover` still takes the modern path.
- `bridge`: the end of the input in `bridge.embed`. The legacy path stops as `Frontend.shutdown` does. The modern path ends the listen streams of the server, and it waits for the other requests for at most `shutdown_grace`. Then it fires the cancel tokens of the requests that are left and cancels their tasks. Thus a handler that examines its cancel token also stops without a cancel point. `serveStdioAuto` returns after this bounded stop, and it arms no watchdog.
- `bridge`: the limit of requests in flight in `bridge.embed`. On the two paths, the reader never waits for a free slot, and a request above the limit gets -32603 at once. Thus the reader always reads the cancellations and the end of the input, also while listen streams hold all slots. The two paths take their limits from `server.options.limits`.

### Security

- `bridge`: the one-time start URL of `bridge.oauth` (M6). When `SignIn` opens a browser, it makes a token of 256 random bits with the secure random source of `Io`, as `OAuthClient` makes its `state`. `Receiver` serves the path `/start/<token>` on the redirect port. On each system, the browser opener gets only `http://127.0.0.1:<port>/start/<token>`. This also applies to `ShellExecuteW` on Windows.
- `bridge`: the sign-in line on stderr still has the authorization URL (M6). With `--no-browser`, and for a URL elicitation after `notifications/initialized`, the receiver serves no start path.
- `bridge`: the answers of the start path (M6). The first `GET` gets 303 to the checked authorization URL, with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, no body and `Connection: close`. A second `GET` gets 410 and stops the sign-in with the reason `start_reused`. The wait ends after the receiver sent that page.
- `bridge`: a start path with a different token gets 404 and does not stop the sign-in (M6). The compare of the token takes the same time for each token. The start path does not work after the time limit of the sign-in.
- `bridge`: after the sign-in received a redirect with a code, a second `GET` of the start path cannot stop the sign-in (M6). The receiver then writes a warning, and its page tells the user that another program possibly signed in with a different account.
- `bridge`: the error cause `sign_in_start_reused` (-32603) in `bridge.translate`. Its message names the host of the bridge and `--no-browser`.
- `vscode`: the start URL and its residual risk in `SECURITY.md` and in `bridges/vscode/README.md`. Another local user can read the start URL and send the first `GET`. That user can then sign in with a different account before the browser of the user sends its `GET`. Then the bridge gets the code of that account. On a host that other users share, use `--no-browser`.
- `vscode`: `bridges/vscode/README.md` has the new lines of the Output channel and the new error message of M6. The status sections of `README.md` and `bridges/vscode/README.md` name M6.
- Repository: the tests of M6. The unit tests of `bridge.oauth` cover the start path and a guess of the token. They also cover a second `GET` during the wait and after the redirect, and the page before the stop. The transcript tests and a process test check that the opener gets only the start URL. In the process test, a `BROWSER` script starts `bridge-fixture-server --browse`, the browser of the test.
